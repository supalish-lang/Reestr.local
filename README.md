# Реестр входящих заявок

Веб-страница для учёта писем-заявок на рассмотрение проектов. Страница лежит на GitHub Pages (`https://supalish-lang.github.io/Reestr.local/`), данные, вход и права доступа обеспечивает Supabase.

Сотрудникам не нужны аккаунты GitHub, Supabase или Claude: достаточно ссылки и рабочей почты `@ot.kz`.

## Файлы

| Файл | Назначение | Загружать в GitHub |
|---|---|---|
| `index.html` | вся страница | да |
| `supabase.js` | библиотека Supabase (`@supabase/supabase-js` 2.119.0, `dist/umd/supabase.js` из npm). Хранится рядом со страницей, чтобы не зависеть от внешних CDN | да |
| `migration.sql` | таблицы, роли, регистрация, администрирование, права доступа, праздники. Выполняется в Supabase | да (для истории) |
| `migration_v4.sql` | работа без почты: временный пароль от администратора, обязательная смена при входе, «заглушка» для писем Supabase | да (для истории) |
| `migration_v3.sql` | переназначение заявок руководителем/администратором, импорт, поле «кто зарегистрировал». Выполняется в Supabase после `migration.sql` | да (для истории) |
| `README.md` | эта инструкция | да |
| `schema.sql` | первая версия схемы, больше не нужна (всё вошло в `migration.sql`) | нет |

## Роли

| Роль | Что может |
|---|---|
| Ожидает подтверждения (`pending`) | только что зарегистрировался; видит экран «Ожидайте подтверждения администратором», заявок не видит и не создаёт |
| Исполнитель (`executor`) | видит, создаёт, меняет и удаляет только свои заявки, меняет их статус |
| Руководитель (`manager`) | видит все заявки; создаёт заявки на любого исполнителя, переназначает их и правит поля; импорт из Excel; выгрузка в CSV. Статус чужой заявки не меняет, чужие заявки не удаляет |
| Администратор (`admin`) | всё, что руководитель, плюс вкладка «Администрирование» и удаление любых заявок |

Статус заявки меняет только её исполнитель. В карточке заявки видно, кто её зарегистрировал.

Права проверяет сама база данных (Row Level Security), а не только интерфейс: даже прямой запрос к API не позволит обойти роль.

Сроки: рекомендуемый срок = дата поступления + 5 рабочих дней, крайний = + 15 рабочих дней. День поступления не считается, суббота, воскресенье и даты из таблицы `holidays` пропускаются. Сроки считает база, вручную их не изменить.

## 1. Настройка Supabase (один раз)

### 1.1 Выполнить `migration.sql`

1. Откройте проект в supabase.com → **SQL Editor → New query**.
2. Вставьте **весь** текст `migration.sql` и нажмите **Run**.
3. Внизу появится строка «Готово» с проверкой: администраторов должно быть 1, а два расчёта сроков должны показать `2026-11-23` и `2026-12-22`.

Файл можно выполнять повторно: заявки и профили он не удаляет. Пользователь `a.yussupov@ot.kz` становится администратором.

### 1.2 Authentication → Sign In / Providers → Email

- **Allow new users to sign up**: **включить** (иначе саморегистрация не работает). В первой версии инструкции его просили выключить.
- **Confirm email**: рекомендуется **выключить**.
  - Встроенная почта Supabase отправляет очень мало писем (несколько в час на весь проект), письма подтверждения легко упереться в лимит.
  - Защита от посторонних всё равно есть: регистрироваться можно только с адресов `@ot.kz` (проверяет база), а новый пользователь ничего не видит, пока администратор не назначит ему роль.
  - Особенность: без подтверждения почты человек может зарегистрироваться на чужой адрес `@ot.kz`. Поэтому администратор одобряет только тех, кого знает (ФИО и e-mail видны во вкладке «Администрирование»).
  - Если подтверждение включено, страница после регистрации попросит открыть письмо и затем войти.
- **Minimum password length**: можно указать 8 (страница и так требует не меньше 8 символов).

### 1.3 Работа без почты (`migration_v4.sql` и Send Email hook)

Почтовые ящики `@ot.kz` нашим не принадлежат, поэтому реестр **не отправляет писем**:
- «Подтверждение e-mail» выключено (п. 1.2), а адрес служит только логином;
- забытый пароль сбрасывает администратор на сайте (п. 4);
- письма Supabase отключены полностью, чтобы ссылки для входа или сброса пароля не попадали в чужие ящики.

Порядок:
1. **SQL Editor → New query** → вставить весь `migration_v4.sql` → **Run** (внизу «Готово (v4)»).
2. **Authentication → Hooks** (в некоторых версиях **Auth Hooks**) → **Add hook → Send Email hook** → тип **Postgres** → схема `public` → функция `send_email_noop` → **Create / Save**.
   После этого Supabase не отправляет ни одного письма (регистрация, сброс пароля, magic link).
3. Если хук когда-нибудь отключат, письма снова пойдут на адреса `@ot.kz`. Включать «Confirm email» без настоящей почты нельзя: никто не сможет подтвердить адрес.

Site URL (**Authentication → URL Configuration**) можно оставить `https://supalish-lang.github.io/Reestr.local/`: без писем он не используется.

## 2. Публикация на GitHub Pages

1. В репозитории `supalish-lang/Reestr.local` нажмите **Add file → Upload files** и загрузите `index.html`, `supabase.js`, `migration.sql`, `README.md`. Нажмите **Commit changes**.
2. **Settings → Pages → Build and deployment → Deploy from a branch → `main` / `(root)` → Save**.
3. Через 1–2 минуты сайт откроется по адресу `https://supalish-lang.github.io/Reestr.local/`. Эту ссылку отправьте сотрудникам.

В публичном репозитории код страницы виден всем. Это нормально: в нём только публичный Publishable key, а заявки защищены правами доступа в базе. **Secret key (service_role) и пароль базы никогда не вставляйте в файлы.**

Если страница показывает:
- «Не заданы ключи Supabase» — в начале скрипта `index.html` пусты `SUPABASE_URL` / `SUPABASE_KEY`;
- «Не загрузилась библиотека Supabase» — рядом с `index.html` в репозитории нет файла `supabase.js` (или он ещё не опубликован, подождите пару минут и нажмите Ctrl+F5).

## 3. Регистрация и одобрение сотрудников

1. Сотрудник открывает сайт → **Зарегистрироваться** → ФИО, рабочий e-mail `@ot.kz`, пароль (не короче 8 символов) дважды.
2. Он сразу попадает на экран «Ожидайте подтверждения администратором».
3. Администратор открывает вкладку **Администрирование** (рядом с ней счётчик ожидающих), выбирает роль, при необходимости исправляет ФИО и нажимает **Сохранить**.
4. Сотрудник нажимает «Обновить» (или обновляет страницу) и получает доступ.

Ограничения, которые проверяет база:
- нельзя снять роль администратора у последнего администратора (в том числе у себя);
- допустимы только роли `pending`, `executor`, `manager`, `admin`.

Закрыть доступ сотруднику: назначьте роль «Ожидает подтверждения».

Удалить пользователя полностью (если нужно): Supabase → **Authentication → Users** → строка пользователя → меню «…» → **Delete user**. Если у него есть заявки, база не даст удалить его, пока эти заявки не удалены или не переданы (передача делается только через SQL Editor). Обычно достаточно роли «Ожидает подтверждения».

Сменить домен почты: в начале `migration.sql` функция `allowed_email_domain()` — замените `'ot.kz'` и выполните файл снова; в `index.html` поменяйте подсказку `EMAIL_DOMAIN`.

## 3а. Работа с заявками

- **Разделение по типу**: переключатель «Все / В пул / На проект» справа от вкладок (с количеством заявок). Он действует на виджеты, таблицу, выгрузку CSV и аналитику; выбор запоминается в браузере. Новая заявка и импорт по умолчанию получают выбранный тип.
- **Виджеты** над таблицей: открытые, истёк крайний срок, рек. срок истекает, поступили за 7 дней, исполнено за 30 дней. Нажатие на виджет включает соответствующий фильтр.
- **Вкладка «Аналитика»**: статусы, доля типов, поступление по неделям, ближайшие крайние сроки (нажатие открывает заявку в списке), нагрузка исполнителей (для руководителей).
- **Сортировка**: нажмите на заголовок колонки. Клавиша `/` переводит курсор в поиск.
- **Тема**: кнопка в шапке переключает «как в системе» / светлая / тёмная.

### Импорт из Excel (руководитель и администратор)

1. Кнопка **Импорт** → ссылка «шаблон» скачивает файл с нужными колонками: № письма, Дата поступления, Тип, Поставщик, Краткая суть, Товары, Исполнитель, Статус.
2. Заполните в Excel. Исполнителя можно указать ФИО, фамилией (если она уникальна) или e-mail. Тип: «В пул» / «На проект». Статус можно не указывать (будет «Новая»).
3. Либо сохраните как **CSV UTF-8** и выберите файл, либо выделите строки вместе с заголовком в Excel, скопируйте и вставьте в поле.
4. В предпросмотре видно каждую строку и ошибки (дубль номера, неверная дата, неизвестный исполнитель). Строки с ошибками пропускаются, остальные загружаются кнопкой **Загрузить**.

Подойдёт и файл, выгруженный кнопкой CSV из самого реестра.

## 4. Пароли

- **Сменить пароль**: кнопка «Сменить пароль» в шапке (у любого вошедшего пользователя).
- **Забыли пароль?** Писем нет, поэтому ссылка на экране входа подсказывает обратиться к администратору.
- **Сброс администратором**: вкладка «Администрирование» → у сотрудника кнопка **Пароль** → сайт предлагает случайный временный пароль (можно ввести свой, не короче 8 символов) → **Задать пароль**. Передайте пароль сотруднику лично (не по почте и не в общем чате). При входе с ним сайт откроет окно «Придумайте свой пароль», и пока сотрудник его не задаст, работать не получится. Открытые сеансы сотрудника на других устройствах завершаются.
- Писем «Send password recovery» из панели Supabase не используйте: они уходят на адреса `@ot.kz` (а при подключённом хуке не отправляются вовсе).

Если когда-нибудь появится настоящая почта: отключите хук (п. 1.3), подключите SMTP (**Authentication → Emails → SMTP Settings**) и в `index.html` поставьте `EMAIL_RECOVERY = true` — вернётся сброс пароля по письму.

## 5. Праздники

Рабочие дни считаются без суббот, воскресений и дат из таблицы `holidays`. В `migration.sql` внесены будние нерабочие дни 2026–2027 годов по:
- Закону РК «О праздниках в Республике Казахстан» (https://adilet.zan.kz/rus/docs/Z010000267_), с изменениями от 11.06.2026 № 306-VIII: с 01.07.2026 День Конституции 15 марта, 30 августа больше не праздник;
- ст. 85 Трудового кодекса РК (7 января и первый день Курбан айта — выходные без переноса);
- официальному календарю 2026 года на gov.kz (https://www.gov.kz/article/33969?lang=ru);
- календарю ДУМК для Курбан айта (2026 — 27 мая; 2027 — 16 мая, воскресенье).

Даты, выпавшие на субботу или воскресенье, не вносятся, вносится день переноса. **Рабочие субботы расчёт не учитывает.**

Когда Правительство примет постановление о переносах на 2027 год (или ДУМК уточнит дату Курбан айта), сверьте список и добавьте/исправьте даты в SQL Editor:

```sql
insert into public.holidays (day, note) values ('2028-01-01', 'Новый год') on conflict (day) do update set note = excluded.note;
delete from public.holidays where day = '2027-05-03';   -- если дата оказалась рабочей
update public.requests set received_date = received_date; -- пересчитать сроки существующих заявок
```

Раз в год добавляйте праздники следующего года.

## 6. Проверка после запуска

1. Сайт открывается без сообщений о настройке.
2. Регистрация с адреса не `@ot.kz` отклоняется.
3. Новый пользователь видит экран ожидания.
4. Администратор назначает роль, пользователь после обновления видит заявки.
5. Исполнитель A создаёт заявку; исполнитель B её не видит; руководитель видит, но изменить не может.
6. Сроки через праздник: заявка от 14.12.2026 получает рекомендуемый срок 22.12.2026.
7. Смена пароля работает, вход с новым паролем проходит.
8. Снять роль администратора у единственного администратора нельзя.
9. Фильтры работают у всех; CSV открывается в Excel с нормальной кириллицей.

## Ограничения

- Бесплатный проект Supabase ставится на паузу после недели без активности. Тогда сайт пишет «Нет связи с сервером»: войдите в панель Supabase и нажмите **Restore project**.
- Почта не используется: адрес `@ot.kz` — только логин, пароли сбрасывает администратор.
- Рабочие субботы не учитываются.
- Один исполнитель на заявку; передать заявку другому может руководитель или администратор. История смены статусов и вложения не поддерживаются.
